# RoleForbiddenRight — запрещённое право в роли

**Важность:** MAJOR · **Тип:** SECURITY · **Теги:** BAD_PRACTICE · **Уровень:** роль

## Что проверяет

В роли, которая не входит в список исключений `excludeRoles`, включено право из списка
запрещённых `rights`. Правило объединяет семейство из 23 однотипных правил «в роли установлено
право X»: все они отличаются только именем права.

Права читаются из модели mdclasses (`Role.getData().objectRights()`), поэтому проверка одинаково
работает для выгрузки конфигуратора и проекта EDT и одинаково обрабатывает оба вида прав:

- права на объект — `<object><name>Catalog.Товары</name>…`;
- права уровня конфигурации — `<object><name>Configuration.ИмяКонфигурации</name>…`
  (`Администрирование`, `РежимВсеФункции`, `ТолстыйКлиент` и т. п.).

Замечание выводится **на пару «роль + право»**: если право выдано на десятки объектов, это одно
замечание, а не десятки. Выключенные права (`value = false`) не считаются выданными.

## Что попадает в отчёт

```
Roles\Оператор.xml: MAJOR [RoleForbiddenRight] В роли "Оператор" установлено запрещённое право "Администрирование"
```

Номер строки не указывается: решение принимает модель, а не разбор XML, и файл права
(`Rights.xml` в выгрузке конфигуратора, `Rights.rights` в проекте EDT) может отсутствовать.
Откройте права роли, чтобы найти место выдачи. `mdoRef` равен `Role.<Имя>` — проверку можно
исключить по роли целиком.

## Параметры

| Параметр | Тип | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `rights` | string[] | 23 права из таблицы ниже | Запрещённые права |
| `excludeRoles` | string[] | `["ПолныеПрава", "FullAccess", "АдминистраторСистемы", "SystemAdministrator"]` | Роли, которые не проверяются |

Значения `rights` принимаются в трёх написаниях без учёта регистра:

- имя константы `RoleRight`: `INTERACTIVE_DELETE`, `DELETE`;
- английское название права: `InteractiveDelete`, `Delete`;
- русское название, как в конфигураторе: `ИнтерактивноеУдаление`, `Удаление`.

Пользовательский список `rights` **заменяет** значения по умолчанию, а не дополняет их.
Чтобы отключить находки, задайте пустой список:

```json
{
  "checks": {
    "parameters": {
      "RoleForbiddenRight": { "rights": [] }
    }
  }
}
```

Имена ролей в `excludeRoles` сравниваются точно, без учёта регистра; пробелы по краям
обрезаются. Шаблоны не поддерживаются: вендорскую роль с префиксом, например `узПолныеПрава`,
нужно перечислить явно.

Неизвестное имя права не участвует в проверке; при запуске в журнал выводится одно
предупреждение с этим значением. Проверка при этом продолжает работать с распознанными правами.

`DELETE` входит в список по умолчанию: прямое удаление данных вне ролей полных прав — такое же
опасное право, как и административные. Если в конфигурации удаление штатно разрешено
операторским ролям, уберите `DELETE` из `rights` или добавьте эти роли в `excludeRoles`.

Значения по умолчанию видны в выводе `checkushka describe-check RoleForbiddenRight`,
а полный список прав модели — в перечислении
`com.github._1c_syntax.bsl.mdo.support.RoleRight` (mdclasses 0.22).

## Пример настройки

Запретить только интерактивное удаление и запуск тонкого клиента, исключив ещё и роль
`узПолныеПрава`:

```json
{
  "checks": {
    "parameters": {
      "RoleForbiddenRight": {
        "rights": ["INTERACTIVE_DELETE", "THIN_CLIENT"],
        "excludeRoles": [
          "ПолныеПрава", "FullAccess",
          "АдминистраторСистемы", "SystemAdministrator",
          "узПолныеПрава"
        ]
      }
    }
  }
}
```

## Исключение

Если роль поставляет вендор и менять её права нельзя:

```json
{
  "ignore": [
    {
      "check": "RoleForbiddenRight",
      "mdo": "Role.ОбновлениеИБ",
      "reason": "роль поставщика"
    }
  ]
}
```

## Как исправить

Уберите право из роли в конфигураторе (ветка «Права» роли) или в файле прав роли. Если право
нужно роли по бизнес-логике, добавьте роль в `excludeRoles` либо уберите право из `rights` —
тогда правило перестанет его считать запрещённым для всех ролей.
